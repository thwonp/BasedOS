# spruce on the GKD 350H Ultra

spruce support for the GKD 350H Ultra lives in the spruce fork, https://github.com/theycallmeboxy/spruceOS,
branch `gkd350h-ultra`, until it is merged upstream. It is a normal spruce platform
(`PLATFORM=GKD350HUltra`, family `basedos`), detected from BasedOS's `/etc/baseos-release`.

## Getting it on a card

> **Unofficial builds:** they are not made or supported by the spruce team. Report problems with them
> [here](https://github.com/theycallmeboxy/BasedOS/issues), not to spruce.

Each spruce nightly is built again with the 350H Ultra branch merged
in, by the fork's `gkd350hultra-nightly.yml` workflow, and published on the fork's
[releases page](https://github.com/theycallmeboxy/spruceOS/releases/latest) as
`spruceV<nightly>-gkd350hultra.7z`. It checks spruce's nightly feed every two hours, and builds
again after a change to the branch too. Install it as any spruce release: extract it to the root
of a FAT32 card. The card stays a normal spruce card for your other devices. These builds are made
automatically and aren't tried on the device first.

Update from that page, not from spruce's own updater: that one offers official spruce, which has
no 350H Ultra support yet. After an official update spruce no longer starts on the 350H Ultra until
a build from the fork's page is copied over it.

The platform is standalone: it owns copies of what it needs from other platforms rather than sourcing
or hooking them. Which files and functions it owns, where each came from and why:
`spruce/scripts/platform/basedos/README.md` in the fork.

| Keyboards in SDL apps | BasedOS has no udev, and SDL2 without udev only opened keyboards named in `SDL_EVDEV_DEVICES`: E-Reader and Gallery (`gptokeyb` turns the pad into a virtual keyboard) got no keys. BasedOS's patch 0006 scans `/dev/input` once at start, as udev's first scan would, and takes the classes udev's path takes (keyboards, mice, touch; not joysticks). On the unit (2026-11-19) the Gallery then opened `gptokeyb`'s keyboard and the power and volume keys, not the pad or the motion sensor, and moved on a Right press with no `SDL_EVDEV_DEVICES`. | Display rotation | as on dArkMoss's rotated panels: BasedOS's SDL2 turns the DSI panel with the RGA (ArkOS's Miniloong patch, ROT_270), so SDL apps see 1600x1440 at 0 and the cfg has `DISPLAY_ROTATION="0"`. SDL leaves Vulkan windows alone (as on the Miniloong); apps that draw straight to the panel through VK_KHR_display (RetroArch's Vulkan driver) are turned by BasedOS's Vulkan layer `VK_LAYER_BASEDOS_rotate` (`buildroot/package/basedos-vkrotate`, an implicit layer): they see a 1600x1440 display, draw into landscape images of the layer's, and on present one draw turns each frame onto the 1440x1600 panel. Checked 2026-11-24 in RetroArch: the game, spruce's in-game menu, RetroArch's menu, its notifications and statistics upright, armN64 at 60 fps; the turn takes 1.0 ms of GPU and 0.04-0.06 ms of CPU a frame. `BASEDOS_VK_ROTATE_DISABLE=1` leaves the layer out; `BASEDOS_VK_ROTATE_LOG=1` and `BASEDOS_VK_ROTATE_STATS=1` (times every 300 frames) log it. DSperate doesn't go through it: it drives KMS itself and renders with Vulkan into buffers it imports (its source; not run with the layer, no DS BIOS on the card). Checked: the menu, spruce's message screens (`display_text.elf`), RetroArch, DSperate, PPSSPP. BasedOS's patch 0005 adds a GPU rotation path, used where there is no `/dev/rga` (a mainline kernel) or with `SDL_KMSDRM_ROTATION=gpu`; `SDL_KMSDRM_ROTATION_STATS=1` prints the rotation's time every 300 frames (stock: RGA 6.5 ms a frame in SDL's test). In games on stock with spruce (2026-11-18, `tools/dev/rotation-ab.sh`, 60 s a path: Star Fox 64, Sega Rally, Crazy Taxi in RetroArch, Burnout Legends in PPSSPP): RGA 2.1 ms a frame, steady; GPU 2.2-2.4 ms with stalls of 10-31 ms every minute or so (the game's own GPU work in the way); the games' frame pacing was the same on both. RGA stays the default. Since c0a58d1 the RGA path waits for the game's frame to be finished before copying it (Mali puts no implicit fences on the buffers, so it could otherwise copy a half-drawn frame); measured at 0.01-0.1 ms a frame |

Listed for `BASEDOS`: the app (spruce fork 0a7cce7ff) and `Emu/PORTS`. Ports tried on BasedOS's Buildroot userland (0ee75de and later, 2026-11-19): DevilutionX, Celeste Classic (native), A Key(s) Path (Godot) and 6 Feet Under (GameMaker on .NET, after its one-time patcher) run upright with the pad; Quake (a RetroArch-core port) runs at 60 fps through BasedOSCommon's run_basedos_port, which, as spruce does for the A30, runs a copy of the port's script whose retroarch call is spruce's own RetroArch with this platform's config (the scripts otherwise call /usr/bin/retroarch, which BasedOS doesn't have); A7Xpg runs (2026-11-23): it needed FLAC 1.3's `libFLAC.so.8` (BasedOS's `flac13` package) and then showed only black, because it calls `SDL_SetVideoMode` every frame (it re-applies one stored `SDL_VIDEORESIZE`, which SDL sends once since KMSDRM's window is the panel's size, not the 640x480 it asks for) and SDL recreated its surfaces each time, discarding the frame: BasedOS's SDL2 patch 0007 keeps them when the mode doesn't change; Apotris runs, with sound (2026-11-23): its audio library, SoLoud, loads SDL by `dlopen("libSDL2.so")`, the development name, and without it ran silent and crashed when the first game, or the title screen's demo 11 s in, began (BasedOS now has the `libSDL2.so` link; the rumble PWM it can't open is harmless); Weston ports work (Alex the Allegator 4: upright, full screen, pad checked; 2026-11-19). PortMaster's westonwrap.sh always preloads its Crusty layer for the drm backend, which fakes DRM/GBM for Weston and draws through SDL2; it needed three things, found with gdb and strace: (1) the unversioned `libudev.so` (Crusty loads libudev by that name, and without it its `udev_new()` resolved to itself and Weston spun forever); (2) `CRUSTY_LIBSDL` set to BasedOS's SDL2 (spruce fork's run_basedos_port): westonwrap.sh otherwise takes PortMaster's own libSDL2, first on the library path, and Crusty tells its SDL's calls from the program's by only the first memory range of the library, which in that build isn't its code, so Crusty faked SDL's display device too and recursed until out of files (BasedOS's SDL2 has its code first, and turns the picture for this panel); (3) udev's database, for libinput: Weston won't start without input devices. BasedOS doesn't run udevd, so `basedos-udev start|stop` runs eudev's udevd (input rule only) for the length of a Weston port, and run_basedos_port calls it for ports that use westonwrap.sh. Quitting (Select+Start) sends SIGTERM to westonwrap.sh along with the game, so the port's script unmounts the pack while the game is still exiting, and the game could be left behind (once hung for good in its own SIGTERM handler); run_basedos_port ends what's left of a Weston port's process group 3 s after it and unmounts the pack (ports without the pack exit cleanly: Celeste Classic, DevilutionX). Crusty also never replaces its `/tmp/CRUSTY_LIBSDL64.so` link once made (a changed `CRUSTY_LIBSDL` takes a reboot); both Crusty points are for Westonpack's author. 32-bit ports (2026-11-19, docs/lib32.md): with BasedOS's `/usr/lib32`, PortMaster lists its ~200 32-bit-only ports (most are GameMaker on the 32-bit gmloader); 7 of 8 ready-to-run ones tried run upright with the pad, the eighth (Sulka) lacks a library in its own package |
